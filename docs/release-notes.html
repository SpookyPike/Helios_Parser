Release Notes

HELIOS Parse / View 2.2.0, released 2026-11-05. Code developed by Dmitrii Bespalov at European XFEL.

Documentation Index User Guide Developer Guide README

Why 2.2.0

Two things stood between a user and an answer: the deck had to be converted first, and the parse itself cost nine seconds on the largest reference deck. This release removes both. The diagnostics commands read a raw .log, .bpf or HDF5 .exo directly, and a native field-table parser cuts the conversion of that deck from 9.03 s to 2.67 s.

The native parser is optional. It ships as a small library beside the package; without it the parser runs the existing Python path at the old speed, so a source checkout needs no Rust toolchain and an unsupported platform loses speed rather than function.

Highlights in this release

  • helios_diag inspect, stats, query and analyse accept an unconverted deck, so parameters, densities, temperatures and the derived modules are readable without a conversion step
  • a native LOG field-table parser: the 530.7 MB reference deck parses in 2.67 s instead of 9.03 s, and write_hdf5 drops from 8.43 s to 3.93 s, with a byte-identical output digest
  • the cycle-header scan no longer walks the whole buffer with one regex: 2.12 s to 0.32 s, identical block spans
  • analyse --breakout-fraction replaces the fixed 0.5 threshold; the default reproduces the previous breakout time exactly

Why 2.1.0

The library could already answer questions about a converted run; the command line could only convert. Everything below was reachable through Python and nothing else. This release puts the same surface on a command line, with an output contract an agent can consume without parsing prose.

The contract is the point. Every command writes JSON to stdout, logs to stderr, and carries enough context to be read by someone who has never seen the source deck: the geometry, the versions, the units, the coordinate semantics, the accounting, and a note for everything it could not determine. A unit is never guessed. On the largest tracked run a per-zone statistic takes 52 ms and reading one field takes 3 ms, so the diagnostics are cheap enough to run while thinking.

  • helios_diag inspect reports the deck setup, the laser pulse, and every field with its unit and shape, without reading field data
  • helios_diag stats gives per-zone or per-snapshot statistics, including the time each zone peaked
  • helios_diag query extracts a profile, a time trace, or the snapshot nearest a requested time
  • helios_diag diff compares two conversions dataset by dataset and exits 7 when they differ
  • helios_diag validate checks a file against the writer contract and exits 7 on a failed check
  • helios_diag analyse runs the derived modules without the desktop application
  • the converter gains distinct exit codes, a JSON summary, stage progress, and batch conversion
  • an agent skill ships with the repository, and a test keeps it matching the binary

Why 2.0.2

A conversion can be compressed, and the compression was leaving a third of the saving on the table. The HDF5 shuffle filter reorders bytes inside each chunk so that the high bytes of a float64 column become a long run of identical values, which is what a compressor can actually exploit. The writer never enabled it.

Measured end to end on the largest tracked deck, a 530 MB log of 1501 snapshots by 1200 zones, pinned to the P-cores: LZF goes from 184.4 MB to 118.6 MB, a 35.7 % saving, for 2.6 % more write time. Under gzip the same filter costs 3 %, from 102.2 MB to 105.2 MB, so it stays off there. Nothing else changes: a default conversion is still uncompressed, and every stored value is identical.

  • the shuffle filter is enabled for --compression lzf and left off for --compression gzip, decided by the filter name rather than by the caller
  • LZF on the largest deck: 184.4 MB to 118.6 MB, a 35.7 % saving, 65.7 MB
  • a run short enough that each dataset is a single small chunk goes the other way: the 8-snapshot tracked fixture grows 8.5 %, from 1.53 MB to 1.66 MB. That is 130 kB against 66 MB, so the trade is deliberate
  • no new dependency, no reader change, and uncompressed output is byte-identical to 2.0.1

Why 2.0.1

The HDF5 writer refused every Exodus run from a deck that leaves the frequency-resolved radiation output off. That is the default deck, and every production deck in the campaign uses it, so this blocked ordinary runs.

A flag-off run still carries the nine radiation families, and they are empty: (0,) for the per-dump arrays and (0, n_zones, 250) for the spectral ones. HDF5 requires every chunk dimension to be at least 1 and at most the data extent, and the chunk helpers clamp the zero axis to 1, so create_dataset refused with Chunk shape must not be greater than data shape in any dimension. (1, 251) is not compatible with (0, 251) and the writer aborted the whole file rather than the family.

  • zero-extent arrays are written contiguous and uncompressed; the axes are kept, so a consumer reads "this family is empty" rather than "this family is missing"
  • the guard sits in the one function every array dataset routes through, so it covers the radiation, flux and diagnostic families together
  • non-empty arrays are unchanged: still chunked, still compressed
  • a new fixture is real 12.0.0 output from the default deck, and the pre-fix writer reproduces the production error on it exactly

Why 2.0.0

The converter, the reader and the derived analysis were slow in ways that were measurable but not visible: a regex scan that cost half a log conversion, one HDF5 write per field per snapshot, and a grid search that called a least-squares solver 55,200 times. This release fixes those, and three of the fixes are large enough to change how the application feels on a real deck.

It also corrects a fixture problem. The golden HDF5 files shipped with the tests stored the log's Radius column, which is a zone edge, where zone centres belong. Every reader test compared the writer with itself, so nothing caught it. The fixtures were regenerated and checked against the source logs rather than against the previous files.

Highlights in this release

  • per stage on the largest tracked deck, 701 snapshots by 1300 zones: log conversion 16.84 s to 6.01 s, BPF conversion 4.72 s to 0.87 s, derived analysis 12.41 s to 1.94 s, so the full log-to-analysis path 29.25 s to 7.95 s
  • HDF5 schema 2.2 changes chunk geometry only: field chunks span 32 snapshots so one writer flush fills one chunk, and radiation chunks span one dump so a single-dump read no longer inflates sixteen
  • scipy is a required dependency. It was preferred but undeclared, so a clean install silently ran a 1537-point complex quadrature at 25.4 ms per call instead of wofz at 0.090 ms. This moves plasmon numeric values for anyone who was on the fallback. The About dialog names the active backend
  • the derived cache key split in two, so a plasmon or XRD edit reuses the shock and wavefront work instead of recomputing it: a plasmon-only edit drops from 0.94 s to 0.002 s
  • the snapshot slider emits once per drag instead of once per intermediate value, and an unchanged colormap is no longer re-resolved on every repaint
  • the six golden fixtures were regenerated and are now validated against the source logs by tests/test_log_truth.py
  • the tree is ruff-clean under an enforced rule set, which surfaced two real misplaced-import defects

Why 1.4.0

HELIOS writes the whole spectral radiation field when a deck asks for it, and the parser used to drop every one of those arrays without saying so. This release reads them, publishes them under their own time axes, and adds a Radiation tab so the boundary spectra can be inspected without a script.

Highlights in this release

  • the Exodus reader maps the 18 frequency-resolved radiation datasets, which it previously discarded
  • the spectral field and the boundary spectra live in two HDF5 groups because they sit on two different time axes: radiation/ on time_freq, flux/ on time_whole
  • metadata/radiation_output is on or off on every converted .exo, so an absent block is distinguishable from a failed read
  • a Radiation tab in Derived / Analysis shows one boundary-spectrum profile per flux dump, plus the boundary flux and the radiation loss against time
  • integrate_over_groups, spectrum_at and spectrum_map in helios.services.derived, and scripts/plot_radiation.py for report figures
  • the two per-group array families use opposite normalizations and the container labels both "per eV"; the converted file records which is which in a normalization attribute
  • HELIOS 12.0.0 log parsing and the Exodus core-field reader, which shipped in 1.3.1 and had no release of its own

Why 1.3.0

This release adds an optional native XCOM 3.1 provider to the experimental Transmission workflow while keeping covered calculations on the fast, in-process cold-XCOM tables.

Highlights in this release

  • optional native XCOM 3.1 subprocess support for neutral elements and mixtures through Z=100
  • table-first calculations for covered requests, with native fallback for supported requests outside the table domain
  • bounded native request batching, result caching, cancellation, and subprocess cleanup
  • clearer Transmission units, provider status, and applicability guidance in the interface
  • cross-platform native packaging hooks; public release packages retain the lookup tables and omit native payloads pending redistribution review
  • documented table provenance, native provider behavior, and scientific limits

Known validation limits

  • XCOM remains a neutral-atom cold baseline. The interpolation tolerance does not establish physical accuracy for warm dense matter or near-edge chemical structure.
  • The native Orca screen-reader and keyboard walkthrough remains unverified. Automated accessibility checks and Windows UI checks pass.
  • Performance comparisons found no repeatable median regression above the review threshold, but speedup measurements for several scenarios remain inconclusive.
  • The flag-off fixture covers the Exodus reader and writer only. The log and BPF paths write the same radiation families and have no flag-off fixture: every tracked log fixture either carries real spectral data or predates the schema.
  • The writer is tested against empty families. Reader, derived analysis and viewer behaviour on a zero-length family is asserted only where the conversion tests exercise it.
