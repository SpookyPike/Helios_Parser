The two-tier gate

The suite is driven by scripts/run_test_suite.py, not by test discovery. It has exactly two profiles and they exist for different moments: 

# commit gate: ten entries, about 15 s
.venv/bin/python scripts/run_test_suite.py --profile core

# milestone gate: every discovered entry, about 17 min, with the coverage floor
.venv/bin/python scripts/run_test_suite.py --profile full --coverage

# one entry while iterating
.venv/bin/python scripts/run_test_suite.py --profile full --only test_reader.py

The core gate is a fixed list in CORE_NAMES: smoke_test.py, test_bpf_pipeline.py, test_chunk_layout.py, test_test_runner.py, and the five command-line entries test_cli_contract.py, test_cli_errors.py, test_cli_stats.py, test_cli_self_description.py and test_cli_diff_validate.py. Add an entry there only if it runs in a second or two and would catch a mistake you would otherwise ship.

--only overrides --profile, so --only without --profile full leaves HELIOS_RUN_SLOW_TESTS unset and silently skips every slow class. Use --profile full --only.

Exit codes: 0 pass, 1 failure, 2 failure with entries not executed, 3 coverage floor missed, 124 per-entry timeout, 125 fixture hash or size mismatch, where the entry never runs. A 125 means the manifest and the file on disk disagree; regenerate the fixture rather than editing the hash.

Each entry runs in a materialised copy of the tree that contains only the fixtures declared for it in tests/fixture_manifest.json. A fixture that is not declared is simply absent there, so the entry errors instead of skipping. pytest is not installed: run a module directly from inside tests/, or through the runner.

Use targeted runs for the area you touched before falling back to broad suite execution. When a change affects shell/viewer/derived routing, you usually need both a focused derived test and at least one shell-level test.

What to run for common changes

Parser, reader, schema

Run coordinate, run-status, reader, and smoke coverage. Use at least one real damaged/truncated or legacy-style file if the parser changed.

Conversion output or chunk layout

Run test_chunk_layout.py and test_log_truth.py, then the streaming and BPF pipeline entries. If the chunk extent or the schema version moved, scripts/regenerate_golden_fixtures.py verifies a fixture against the source log and refuses to replace it unless every value and the centre/edge contract survive.

UI interaction cost

Run test_ui_interaction_perf.py with --profile full. It asserts call counts rather than timings, so it does not flake on a loaded runner. For the visual half, scripts/capture_ui_evidence.py writes PNGs and an HTML contact sheet under outputs/screenshots/perf2/.

Viewer layout or settings

Run viewer phase tests, shell settings propagation, and manual screenshot validation for the touched workflow.

Derived orchestration or caching

Run backend optimization, derived stability, and WaveFront/Preheat UI tests. Check that legacy Shock is still fast and that advanced tabs remain lazy.

Plasmon/XRTS spectral work

Run the plasmon phase and UI suites, then use the validation scripts for benchmark overlays, cache reuse, snapshot refresh, and LOS-vs-effective-state checks before shipping docs or UI claims.

WaveFront or Preheat UI

Run test_wave6_derived.py, then do manual visual validation on at least one real run where the affected advanced tab has meaningful content.

Manual QA expectations

Automated tests are not enough for major UI or orchestration changes. Manual QA is expected when:

  • tabs, selectors, splitters, or scroll behavior changed
  • busy/progress behavior changed
  • WaveFront or Preheat UI changed
  • screenshots or docs are being updated
  • a fix is explicitly about interaction feel or stale UI state

Performance and timing checks

Use the existing instrumentation rather than guessing. Important checks include:

  • legacy Derived open remains fast
  • WaveFront first-load timing is visible and cached reopen is meaningfully faster
  • Preheat reuses WaveFront/interface context and does not force full recompute on ROI-only changes
  • snapshot browsing stays lightweight after advanced data are already loaded
  • heavy background work still shows progress/busy feedback
python scripts\bench_wave6_derived.py
python scripts\microbench_wave1.py
python scripts\bench_streaming_conversion.py
python scripts\bench_hdf5_access.py

A/B on the same machine with a warm page cache, three runs, report the median, and digest the output so a faster wrong answer is visible. On a hybrid CPU, pin to the P-cores: the reference host is a 12th-gen Intel where CPUs 0-11 are the six P-cores and their SMT siblings, and running on the E-cores roughly doubles a conversion. run_test_suite.py already pins itself; do the same for a hand-run benchmark with taskset -c 0-11.

Report absolute milliseconds alongside any ratio. Several 2.0 audit findings were measured and dropped for exactly this reason: a per-snapshot coordinate memo bought 1.7 % of a 79 ms scrub, an 8 MiB HDF5 chunk cache measured neutral to slightly worse on uncompressed datasets, and a snapshot re-read costs 6.6 us. A ratio on a microsecond operation is not a win worth carrying.

Definition of done for nontrivial work

  1. The touched backend/UI path has focused automated regression coverage.
  2. Smoke coverage still passes.
  3. Manual QA was performed for interaction-heavy changes.
  4. Busy/progress and cache/lazy behavior still match the intended UX.
  5. Documentation was updated if the visible behavior or workflow changed.

For large features, also keep at least one real-file validation note. The most common late regressions are not numerical; they are stale state, lazy-load drift, broken tab ownership, and settings propagation mismatches.
